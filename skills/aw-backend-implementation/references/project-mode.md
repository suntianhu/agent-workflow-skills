# 任务判断、技能采纳与模型选择

有目标项目时先读其受影响目录的 AGENTS.md，检查相关工作区修改、已有栈、入口和命令；独立设计产物只核对本次已有材料与可用展示工具，不先要求产品工程。只读参考其他项目不会授权修改其他项目。当前用户明确要求优先于历史项目约定；技能不能改变平台权限。

老项目同时识别已经配置的 Skills、代理/插件入口及规则引用，承接其清单与项目内部规范。后续再启用技能，也先对齐已有梳理、技能采纳与验证决定；新技能默认做法不能让项目规范失去效力。

先用现有信息选择主要能力，只有真实缺口再补技能；不把组合当必跑清单。有效结论和已读资料直接复用，小改内联判断，不额外写报告、估时日志或委派。对用户已有/部分完成的 Skill，先只读评估保留、局部调整或重建；展示具体差异并获得明确确认后才改正文、引用、入口或发现配置；已确认方案直接执行。

## 先判断交付物

只要需求说明、单页视觉稿或独立展示原型时，先按交付范围工作，不把“新页面”自动识别为“新建产品工程”。无目标项目可独立设计；有项目但只看稿时，读取既有规则、设计与本页相关资料即可先形成草案，不要求先完成全仓阅读、选栈或工程规范。实现可行性未核实要标明，不能声称开发门禁已过。

已有产品的新需求仍归该产品，即使只做仓库外稿件，也必须先查看相关旧页面与现有组件/样式，继承原有视觉和交互。缺书面规范不等于可重新选风格；未获改版要求时不改变整体品牌与设计语言。

独立原型在任务产物范围内制作，核对展示与有限交互；编写可运行原型代码或执行自动交互前先确定局部验证，以及交付物/临时验证的保留范围，不默认 TDD 或新增永久测试。原型媒介不代表已选产品栈。只有要求正式实现/接入项目，或实际开始修改产品代码、路由、依赖、配置和真实业务时，才适用下方开发门禁，不能用“先做原型”绕过它。

## 先区分新旧与前后端

先判断目标是否已有业务代码、接口、数据或部署依赖，再判断开发端。已有系统内新增页面、接口或模块仍是老项目；文件夹刚建、目录没文档或开发者第一次接触它，不等于新项目。运营后台的页面、路由与交互属于前端，API与持久化属于后端；跨端任务两边都适用。

老项目开展产品代码、配置、工程脚本开发之前，必须有覆盖当前项目的完整代码理解与内部规范。没有可核对的完整基线时，逐项阅读全部自有代码，不能用 README、扫描、局部检索或编译代替。已有基线时先核对其依据和后续全部差异，补读变化及其直接影响，更新同一规范；覆盖不完整或仍有关键未知时继续调查，不先开发。前后端同仓的基线覆盖两端，实施规范分开记录。

基线有效性按证据与覆盖判断，不按新需求、新聊天或启用技能的次数重置：核对目标仓库/范围、完整阅读记录及指纹或可定位版本、现行规范和基线后全部新增/修改/移除文件及规则变化，隐藏/未跟踪内容也不能漏。读取规范、架构摘要和本次相关代码以承接理解；只有旧聊天的“已读”说法或过期而未补查的记录不算有效基线。架构、依赖、权限或部署变化暴露的理解缺口须补齐，无法证明完整覆盖才重新全仓梳理。纯说明文档可直接核对，不绕过正式开发门禁。

新项目先确认开发语言、平台和约束，再按“新项目框架与开源范本”模块联网推荐；已有明确框架选择就核实，不重复问。未选择前可做需求、设计和只读选型研究，不初始化、不安装候选框架、不擅自替用户选栈。

## 用风险选择流程

| 等级 | 可观察依据 | 本次工作 |
| --- | --- | --- |
| 轻微 | 文案不改业务含义；文档；局部间距不改变点击、遮挡、滚动、状态 | 直接改、核对需求和 diff；不自动设计评审、TDD、截图矩阵或独立代理 |
| 常规 | 单一流程的行为、校验、异步或局部缺陷 | 梳理验收、实现、直接影响路径验证、受影响端工程检查、一次反例审查 |
| 关键 | 鉴权、归属、私有图片、支付、持久数据、迁移、并发、跨端公共契约 | 加查相关边界、失败恢复、兼容和回滚；按测试策略选择验证；范围仍限本次影响 |

风险不由行数决定。改一个权限条件是关键；“移动一点”若涉及固定层级、点击范围或安全区就重新分级。发现复杂度变化时可升可降，以证据解释；风险提高不自动授权发布、恢复测试或扩大业务范围。
