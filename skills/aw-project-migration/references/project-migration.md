# 项目迁移：目标、边界与批次

本流程用于已有产品更换前端或后台框架、服务端语言/架构、ORM 或数据库，并需要保持业务连续性、历史数据或既有调用方。它拥有迁移的保留映射、依赖顺序、共存与切换方案；具体编码、契约、安全和验证仍由对应能力负责。普通局部重构、无兼容要求的依赖升级、只换部署机器，直接使用相应实现/运维流程；只有跨系统兼容、数据搬迁或运行职责转移时才补迁移方法。

## 从用户要保留的价值开始

“换框架”“重构数据库”“按新项目重做”是实现方向，还不能说明成功条件。先查目标项目、已有决定和可用证据，再补会改变方案的问题；已明确的技术栈、保留项和授权不重复询问。只做分析时交付方案和未决项，不因计划中有实现阶段就开始产品改造。

| 用户表达 | 需要核实的真实目标 | 会改变方案的约束 |
| --- | --- | --- |
| 老框架难维护，想换一套 | 维护成本、支持周期、团队技能，还是具体性能问题 | 保留单体是否足够；语言、许可证、部署与运行成本 |
| 页面重新写，接口保留 | 页面体验改变还是只换渲染/组件栈 | 路由、登录态、旧链接、权限、已发布客户端、SSR/SEO 是否需要连续 |
| 后台重做 | 管理界面、服务端，还是两者都换 | 管理员工作流、审计、批量操作、导入导出与服务端边界 |
| 数据库重构 | 仅整理模型/ORM，还是换引擎、拆库或改数据归属 | 历史数据、ID、金额/时间语义、容量、停写窗口、RPO/RTO |
| 旧功能都留下 | 留可观察业务行为，哪些实现允许替换 | 定时任务、外部接口、回调、附件、报表、异常恢复和低频流程 |
| 多智能体一起迁移 | 哪些工作能独立验收、并行能缩短哪条关键路径 | 工具/授权、契约稳定度、共享文件、数据环境和集成责任 |

RPO 是可接受的数据丢失范围，RTO 是恢复时间目标；两者由业务约束确定，未知时记待定，不自行承诺零停机或零丢失。明确范围之外的功能、业务优化和视觉重设计另列，避免在替换技术栈时隐式改变产品。

## 建立可核对的现状和保留映射

沿用项目规范、技能入口及有效完整阅读基线，补齐全部变化与缺失覆盖；没有有效基线时，正式改产品代码前完成全仓理解和内部规范。迁移到新目录仍属于老产品，不能用“新建仓库”跳过旧行为梳理。只读调查先记录已读范围，不把扫描结果称为完整理解。

从用户流程向下追踪页面/管理端 → 请求与服务 → 数据/文件 → 事件/定时任务 → 外部系统；反向核对没有页面入口的处理器、脚本、数据库触发器和部署计划。证据包括源码、运行配置的脱敏结构、现有契约/测试，以及获授权可读的日志/调度平台；README 不是全部事实。运行中但不在仓库里的任务标为未核实，不能默认为不存在，也不能索取/复制无关凭据。

为每个业务能力、接口、任务和数据对象记录稳定 ID、旧证据、消费者、期望行为、处置、目标落点、依赖、负责人和验收证据。处置使用“保持行为 / 适配实现 / 经批准改变 / 经批准下线 / 待核实”；未知不等于下线，发现旧缺陷不等于必须原样复制。需要改变的可观察行为写清原因、影响及决定来源。细项按需读 [migration-preservation.md](migration-preservation.md)。

## 选择目标及过渡架构

已选目标直接核对影响迁移的支持版本和兼容缺口。尚未选定时，按语言/平台、部署、业务约束和实际迁移成本，查官方维护/发布资料、数据库驱动、ORM、调度器及插件替代能力；给少量候选与证据。没有自主选型授权且选择影响实现时保留待决，继续推进不依赖选择的盘点。获明确委托后记录决定并推进。

新项目框架选型技能的“真正新产品”边界不因新建目标目录自动满足；迁移候选在本方案评估。已选栈后可按需借助 GitHub 范本研究补工程规则，并写回同一项目规范，区分旧系统现状、目标约束和过渡例外。不要用“换框架”自动推出微服务、换语言、换数据库或换登录体系。

| 路径 | 适用证据 | 必须交代的成本/限制 |
| --- | --- | --- |
| 原位演进或模块内替换 | 行为边界较清楚，主要问题可在同一应用解决 | 运行时/依赖兼容、回退版本、受影响消费者 |
| 按业务能力逐批替换 | 能路由/适配，需持续交付且不宜整体切换 | 过渡层、共享身份/数据、共存成本和移除条件 |
| 并行构建后窗口切换 | 范围有界或难以截流，业务接受验证与停写窗口 | 完整演练、最终增量、停机预算和恢复限制 |
| 先换前端/服务端、保留数据层 | 数据风险或团队容量要求先收窄变量 | 旧存储/驱动支持边界及后续是否真的需要换库 |

比较后给推荐和依据，不硬套渐进替换。数据、任务和流量可能需要不同的切换粒度；“页面切到新服务”不能替代后台任务执行权交接。

## 先做贯通样本，再拆有依赖的批次

在已授权实施且门禁满足后，选有代表性、风险可控的一条业务链路，贯通界面/调用方、服务、数据和适用异步任务，确认目标栈、身份传递、部署与兼容方案可行。纯服务端迁移不人为增加 UI。不要把所有页面写完、所有接口写完、最后才第一次联调。

后续批次按业务能力形成可验收单元，可有共享契约、兼容层和数据扩展等前置任务；不要求每批都涉及全部技术层。通用依赖/验收/所有权字段沿用 [task-planning.md](task-planning.md)，迁移再关联保留项、水位、执行权、恢复与停止条件。前端、后台、数据库是工作角色，不能用三个巨型技术任务代替业务分批。

共存、数据迁移与恢复按需读 [migration-execution.md](migration-execution.md)；实际需要委派时读 [migration-agents.md](migration-agents.md)。模板只补真实缺口：复用项目已有计划和台账，不为每个技能再造一套。

## 接回现有能力

| 缺口 | 使用能力与交接 |
| --- | --- |
| 旧项目理解/规范缺失 | aw-repository-audit / aw-project-standards；先沿用有效覆盖 |
| 目标/验收仍不清楚 | aw-requirements-design；交回迁移简报的同一组决定 |
| API、事件、共享配置契约变化 | aw-api-contracts；迁移计划引用已核实契约版本 |
| 身份、权限、租户或私有数据边界变化 | aw-security-boundaries；保留行为不代表保留安全漏洞 |
| 需要实际代码或行为检查 | aw-test-strategy；消费一次有效的范围/TDD/保留决定 |
| 端内实施 | aw-frontend-implementation / aw-backend-implementation；数据与任务实现归后者 |
| 有界委派、审查与交付 | 按需使用 aw-agent-coordination、aw-adversarial-review、aw-evidence-verification |
| 请求集成/发布/真实切换 | aw-release-readiness；区分具体授权与尚待执行的步骤 |

这些名称是本集合的可选能力，单独分发本技能也可由当前执行者完成相应职责，不依赖其他技能、固定代理、供应商或特定工具名存在。
