# 需求与设计头脑风暴

由需求设计拥有方向澄清；不是额外审批技能。先读取现有需求、项目规则、选定技术栈、已有设计和用户已说过的偏好，只处理仍影响结果的缺口。明确的小改直接执行；复杂或方向开放时用以下步骤，不把清单逐题问给用户。

1. 用具体使用时刻说明谁在什么环境完成什么任务；确认成功、非目标、不可破坏的体验和交付范围。区分用户陈述、项目证据与自己的假设。
2. 有价值时定向研究现有产品、代码或设计参考；说明要解决的问题。代码范本交给 GitHub 参考，视觉/交互案例交给设计参考；两者共用已定平台与规范入口。
3. 私下展开若干方向，淘汰违反约束的方案。存在实质取舍时展示 2–3 个不同的任务结构/交互方向，比较收益、代价、风险并推荐；不只换颜色，也不为凑数重开已定方案。
4. 空间、流程或视觉差异难用文字判断时，采用当前工具可实现的流程图、线框、可点原型或并排示例。标清探索稿/假数据，试验留在任务临时范围，不能借原型绕过老项目产品代码门禁或测试政策。
5. 把结论写成目标/关键路径/状态/验收/约束/未决项；复杂项目沿用已有需求文档目录。小改在对话内交接即可，不强制新建固定文档目录。

只询问影响正确性、范围或关键产品取舍的信息，继续不依赖答案的工作。已有授权和选择足以推进时直接实施；缺少必要答案时保持对应部分待定，不把沉默视为同意，也不重复要求批准。发生会改变交付内容的范围增长时说明新影响。

界面需求把方向交给项目设计规范与 UI 设计，非界面需求交给 API/任务/数据设计；不要为了头脑风暴给纯 API 补视觉稿。若请求本身要求比较方案，交付可审查方案后再承接用户选择，不能替用户编造偏好。

文本、静态线框和资料阅读可先行；编写可运行原型代码或执行自动交互前，先内联取得/承接同一次验证策略与临时产物范围，后续 validation-plan 复用该决定，不等流程走到后面才补选。探索产物与目标项目代码仍遵守各自门禁。
