# 项目内规范与公开参考

规范必须位于实际目标项目内，开发时可发现、可追溯并保持更新；本技能集合不能代替每个项目自己的规范。已有规范入口优先使用，内容不足则补全，不制造互相矛盾的第二份。

默认位置 `docs/engineering/PROJECT_STANDARDS.md`，前后端内容可拆为FRONTEND.md与BACKEND.md。使用本包 `assets/project-standards.md` 的字段结构填入真实内容，删除不适用章节并说明依据；未读/未知不能改写成事实。

## 规范目录和项目级 Skill

规范正文与技能入口承担不同职责，但必须指向同一套规则。老项目先查已有规范目录及根/子目录规则引用，继续维护该入口，不平行新建 docs/engineering 副本。新项目也先检查脚手架和团队约定；确实没有既有位置时，才使用上述默认规范目录。

涉及多模块交付时，在同一规范记录模块职责、实际目录、启动命令和工具导入根；用户界面、管理界面与服务端分别归属，服务端不计作另一个客户端。用户指定的工程组织习惯与偏离理由在此承接，不另造目录规范。

涉及目录迁移时，列清源/目标及脚本、锁文件、文档、构建与导入引用，核对私有配置、持久数据及其附属文件的保留/恢复方式；迁移后按约定身份与原有数据复核入口，不把生成一套新状态当作迁移成功。私有资料仍留在其授权运行位置，不进入公开交付包。

需要建立项目规范级 Skill 时，先复用目标项目现有的技能发现目录及命名方式；没有约定时，按当前宿主实际支持的项目级目录确认位置。已有的 .agents/skills 或 .claude/skills 可作为调查线索，不把示例当所有宿主通用路径，不写入用户全局技能目录。多宿主需要适配时只增加薄入口，规范正文保持一个维护源，不为每个宿主复制一套规则。

项目 Skill 的 SKILL.md 只说明项目范围、何时读取、规范正文的真实相对路径、适用子规范及冲突/更新方式，沿用同一技能采纳表和验证决定；可用 assets/project-skill.md 作结构模板。生成后从该文件所在目录解析所有本地路径，确认仍在目标项目内、实际存在并可读取，覆盖前后端与工作区包的实际作用域。不要写本机绝对路径，不把本集合模板或尚未填完的占位符当作项目已建好的 Skill。

交付分别报告“规范已写入”“项目技能入口已建立”“宿主已实际发现”三项证据。入口文件存在不能冒充宿主加载成功；没用到的宿主不建立额外入口。纯规范文档任务不自动扩展为宿主配置安装。

老项目规范来源于可核对的完整代码基线、已补查差异、配置与用户决策；新项目来源于已选定且有决策依据的语言/框架、实际官方文档与成熟GitHub范本。两类都记录日期、版本/提交、规则证据、例外、检查命令和维护方式。已有阅读覆盖但规范待补时，只补规范，不重复全仓阅读；现行规范已覆盖本次约束时直接消费，只有缺失/改变的规则才增量维护，不重新填整份模板。开发前读相关章节，交付前核对偏差。

规范必须承接项目已有 Skills、指令、代理和插件配置清单：来源/版本或指纹、适用目录与触发、实际发现证据、本次采纳状态、职责归属、与项目约束的冲突及处理。未配置时记录已检查的入口范围，不凭缺一个常见目录推断全无。不要把外部技能全文复制进项目规范，用可定位引用和采纳决定保持唯一规则入口。

原有 Skill 即使只写了一部分，也先核对其有效规则、引用和调用方。优先保留/局部调整；合并或重建须给出依据和旧规则迁移方案。修改用户已有 Skill 的正文、资源、薄入口或发现配置前，展示具体差异并获明确确认；未确认先准备仓外候选，不直接覆盖，也不另建冲突的平行入口。已确认范围直接沿用。

后续启用技能须先读取这个入口，对照最新代码/配置变化补查，再回写新增规则或例外。交接至少包含规范位置/依据、既有技能采纳表、当前阶段和未决事项，使后续技能沿用已经成立的项目决定；不把“梳理完成”和“技能启用”变成两条独立工作流。

项目测试约定还须明确各端实际语言/运行时、已有测试根和工具链、精确局部命令、TDD 决定、P0/P1/P2、临时目录及保留边界。临时验证不是默认采用 Python 的理由，项目规范的执行入口应能让后续技能找到同一套测试决定。

涉及界面时，同一入口也应指向项目已有设计规则、token/主题与组件源，以及实际支持的平台。建立或改变共用设计体系时由 aw-design-standards 补齐；已有 DESIGN.md 等规范继续在原处维护，只有无既定位置才在当前规范目录增加设计章节或子文档。设计技能后来启用时也先读同一采纳表、冻结区及验证决定，不建立独立于项目基线的设计流程。
