# 可观测性设计与验证

本技能拥有运行问题到信号的映射、采集/关联/查询设计及信号本身的验收。用户请求埋点、运行诊断、指标/链路/告警或存在具体观测缺口时使用；普通改动不自动全站埋点。已有日志/指标用于定位故障时先用排障，性能瓶颈调查交性能能力；本技能不代替两者。

## 从需要回答的运行问题开始

沿用项目现有观测工具、命名、部署、隐私与保留规则，先查已有信号能否回答问题。明确业务入口、成功/失败语义与诊断目标，再补信号；请求、webhook、调度、手工补跑和队列来源需要可区分，不能把 HTTP 200 或进程存活当业务成功。没有实际缺口就复用，不另建仪表盘或工具栈。

| 问题 | 可选证据及设计要点 |
| --- | --- |
| 哪次操作发生了什么 | 稳定事件和可查询字段，适用关联 ID、入口/版本和结果分类 |
| 多少请求成功、哪里变慢 | 合理分母、单位、窗口与错误率/耗时分布，结合负载和采样口径 |
| 时间花在哪一段 | 相关请求/任务的分段或链路关联，包含异步/外部边界 |
| 作业是否漏跑、积压或反复失败 | 最后成功、运行时间/计划时间、队列年龄、重试/失败与业务结果 |
| 什么情况需要响应 | 有依据的症状/风险阈值、持续条件、去重、恢复判据和责任人 |

按这些问题选择日志、指标、链路或更轻的已有证据，复用项目格式与协议，不强制三种信号都建、全接口覆盖、特定 SDK 或供应商。实际实现前按项目版本核对 API 和运行能力。

## 采集和成本边界

字段按诊断用途最小化，尽量在采集端排除秘密、令牌、完整请求体、私有内容与签名 URL；再核对处理、导出、查询和保留范围。自动采集也需检查实际输出。哈希可预测标识不保证匿名，不把日志/trace 当作可以任意存个人数据的地方。

指标标签控制可枚举维度和总组合数量，避免原始 URL、任意错误文本、用户/请求 ID 等无界值；需要关联的个案放在允许且受控的记录中。说明采样、丢弃/重试、队列、存储与开销预算，分位数/计数的解释受实际样本与采样限制，不能把采样计数冒充业务总量。

沿异步/进程边界传播允许的关联上下文，决定父子或链接关系并按所用协议验证；不要把外部传入的任意 ID 当可信身份，也不借上下文传播带出凭据。诊断管道的失败应有有界资源与明确处置；区分可降级遥测和业务必须成功的审计记录，不能一概吞错或让非必要采集阻塞业务。

采集端点、第三方外传、告警收件人/渠道及真实通知按具体授权处理。允许设计或本地埋点不自动授权上线采集、配置外部账号或发消息；授权已明确则直接继续，不重复确认。只设计时交付字段/流向/预算和待验项，不操作真实系统。

## 告警和信号验收

告警来源于业务症状或必须响应的风险，不照搬固定阈值/级别/天数。每条写清口径、窗口、去重/抑制、责任人、第一步查询与处置入口；复用已有运维手册。噪声/恢复与缺数据也要解释，不能简单把缺失读成零故障。

实际执行前承接验证/保留决定，在允许环境触发适用正常、失败、重试/异步路径并观察实际输出：事件可查、字段与单位正确、关联不断、敏感数据未泄漏、信号量/资源可接受。验证指标查询和告警条件本身，不只确认配置文件存在。模拟通知/隔离演练与真实渠道送达分开报告；未经具体授权不发送真实告警或制造生产故障，也不降低线上阈值来试响。

端内埋点/配置实现仍由实际前/后端工程约束负责，老产品变更保留基线/规范门禁。本技能负责信号设计与验收，不执行第二轮业务实现。组合前置阶段只确定/承接方案，后置只补信号证据；已有部署/查询结果有效就复用。交付按已设计、已实现、信号实际可查、演练通过、真实渠道验证分别陈述，缺口交完成前证据能力，不自动扩成发布。
