# 安全发现的证据整理

仅在本次涉及具体信任边界变更、疑似漏洞或安全差异审查时读取。此资料补充证据的组织方法；安全边界技能核对控制，反例审查技能只读评估，修复仍交实现者。不自动启动全仓渗透、PoC 执行、扫描器安装或多代理流程。

## 把候选发现变成可核对的问题

写清受影响版本/配置、可控制的输入、进入系统的身份、关键处理位置，以及声称会发生的后果。沿实际调用链检查转换、校验、状态、依赖调用和最终敏感操作。每个关键判断附文件位置或真实环境证据；只有函数名或片段时保留未知环节，不能假定 SDK 已防护或必定未防护。

审阅相关路径时记录成立条件及由谁保证。例如 URL 被校验后，SDK 是否重新解析、允许跳转或另建请求；若后续行为不可见，明确缺少的版本、配置或实现。多层链路的摘要应能让接手者定位每一段，不要求为所有函数额外生成文档。

## 变更与反证

比较本次修改前后的控制与直接调用方；删除或替换安全检查时，查相关历史，确认原检查为何存在及替代控制是否覆盖同一风险。使用只读 diff、show、log 等方式读取基线，不为审查切换用户工作区、重置改动或更换分支。按真实可达入口和调用影响判断范围，不以文件数或固定调用方数量判定风险。

针对候选结论，同时查找能使触发成立的条件，以及实际存在的阻断条件；网络出口、框架防护和部署配置都须有证据。不能因“代码看起来危险”就确认漏洞，也不能靠想象中的防护否定它。缺测试、工具报警或相似历史漏洞分别是调查线索，不直接等同本次可利用性或严重程度。

## 输出与后续

每项按可定位的入口与位置、触发条件、已有证据、实际影响、结论和下一步组织，选择与证据相符的状态：

- **证据支持该发现：** 说明已证明的路径和影响，另标静态推导或实际复现，不把两者混用。
- **现有证据否定该主张：** 指出被核实的阻断环节及适用条件；不扩大为系统完全安全。
- **尚不能判定：** 列出阻断判断的具体缺口和最小补证办法，保留候选，不强行二选一。

严重程度按已证实的权限、可达性、资产与后果解释，避免把未知条件升级成确定的最高风险。只读权限下交付静态结论与复核步骤；需要实际请求、扫描或复现时，先满足本次工具、环境和测试政策。P0 不借安全审查恢复自动测试。

例如扫描器在两层未知 SDK 之后标出 SSRF：交付已证实的数据传播段、缺失 SDK/配置及需核对的目标限制；在链路不可见时保留“尚不能判定”。补齐证据后才收敛结论，不能把未复现当作漏洞不存在。
