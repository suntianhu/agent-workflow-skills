# 项目整体设计规范

本技能拥有跨页面/跨端共用的设计规则与维护边界。输入为需求简报、真实平台/选定栈、现有品牌/组件/token、参考采纳及项目规范入口；页面布局与局部反馈由 UI 设计应用。纯 API、后台任务或明确小文案调整不新建设计体系。

只设计独立单页/原型或先看页面稿时，不因缺少项目级规范触发本技能：复用可用约束，本页补够用的局部规则即可。用户明确要求共用设计规范，或正式项目实施需要建立/改变共用规则时才进入下述流程；没有项目规范不是单页设计的阻断。

老项目无书面规范也先从相关现有页面、组件、token/样式和交互提取已有设计，不能当作从零创作。新需求在既有语言内延展；整体风格/品牌改动须来自用户明确范围，不能由新增技能或外部参考自动引入。

区分项目共用规则和业务页面选择：字体/字级体系、颜色语义、间距、主题、图标和通用组件不因业务全新而失效。没有相似业务页就读取实际全局样式和基础组件；本页可新增任务结构/流程，在同一体系内扩展组件。全局 token、字体依赖或主题变更按明确的项目级改版范围处理，单页新需求本身不授权这些改动。

## 先复用唯一规范位置

老项目先读全仓梳理、既有 Skills 和规范采纳表；新项目先核对已有脚手架/团队约定及已选栈。若已有 DESIGN.md、设计系统文档、token 源或组件库，继续维护其实际位置，由现有项目规范入口引用；不能因启用新技能另起一份正文。确无约定时，在已确定的项目规范目录内增加设计章节，内容较多才拆 DESIGN_STANDARDS.md，并从同一 PROJECT_STANDARDS 入口链接。

需要项目级 Skill 时复用该项目实际支持的发现目录，只给同一规范增加薄入口/章节引用。从 SKILL.md 所在目录解析相对路径，确认文件真实可读且仍在项目内。多宿主不复制正文；后续技能变更回写同一采纳表、例外和维护记录。未完成老项目门禁不能借设计技能开始产品代码实现。

## 形成够用的规则

使用 assets/design-standards.md 作为填写结构，删除不适用项。先提取现有设计事实，再标明本次新决定、局部例外和待核实项；不把草案说成实现事实。规范至少回答：

1. 服务谁、核心任务、信息架构/导航、内容层级、品牌与冻结区；运营后台重视密度与批量操作，展示页面按内容和转化任务组织，不能全套同一模板。
2. 色彩语义、文字层级/回退、间距与布局、密度、形状/层级、图标/图片及动效。可按基础值→语义→组件映射，但沿用项目命名和真实源文件；简单项目不用硬建三层、主题或 token 工具链。
3. 组件的用途、变体、数据/输入约束及适用状态；加载/空/错误/权限/禁用/提交结果来自需求契约，不靠成功截图补想象。业务规则仍由需求和实现规范拥有。
4. 实际支持平台、设备/窗口、输入方式、安全区、字号缩放、本地化、主题和辅助功能；读取 design-platforms.md 的适用部分，区分共享规则、平台映射和局部例外。
5. 可访问性与内容规则：真实标签、焦点/读取顺序、非颜色提示、可恢复错误、长文本、日期/金额/单位、减少动态效果。对比/尺寸阈值给目标平台与依据，不把 px、rpx、pt、dp、sp 写成同一个值。
6. 资源许可/来源、真实数据与示例标记、实际工程位置、验证命令与证据边界、规则变更与消费者范围。

具体排版、密度、状态与资源核对需要时读取 ui-system.md；不为每次局部改动加载全部设计资料或重复做体系。

## 规范落地和变更

将规则对应到实际 token/主题/组件文件和组件示例；外部设计文件仅在项目已经采用时记录版本和同步方式，不默认要求 Figma、Storybook 或其他工具。品牌语义可以共用，导航、单位、原生控件和系统交互按平台映射；跨端框架不免除原生约束。

先检查受影响组件和代表页面，公共 token/组件改变才扩展其真实消费者。记录支持范围、检查环境和未验证项：设计文件、源码、浏览器、模拟器/开发工具、真机证据各自成立，不能互代。验证沿用已选测试政策，设计规范不自动生成永久测试或扩大截图矩阵。交付包含规则位置、入口路径、共享/平台/局部边界、采纳依据和实际证据。
