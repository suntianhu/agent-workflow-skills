# 性能调查与优化

本技能拥有性能目标、测量设计、瓶颈证据和改善判断。用户明确要求性能调查/预算，或有具体延迟、吞吐、资源消耗或性能退化症状时使用；普通功能开发、无证据的“顺手优化”不触发。功能正确性故障先按排障定位，已有有效数据直接复用。

## 先界定目标和证据

承接目标端、项目规范和现行基线，说明哪个用户流程/请求/任务慢、什么负载与数据规模下出现、成功口径及本次停止位置。只调查可先读取现有日志/计划/采样结果；实际执行基准、请求或负载前采用有效验证/保留决定和允许环境。修改老产品前仍需完整代码理解与同一规范；不因性能任务跳过门禁，也不为已有目标重新访谈。

先核对原生工具和已有观测能力，选择最低成本的区分证据，不默认安装分析器、上线埋点、访问私有数据或给生产加压。环境不足时提供调查结论和可执行测量方法，标明未实测范围。

## 按症状测量和定位

| 症状 | 优先区分的证据 |
| --- | --- |
| 页面启动/导航慢 | 网络与服务等待、资源加载、主线程/渲染和平台生命周期 |
| 交互卡顿 | 直接操作耗时、长任务、布局/重复渲染及设备条件 |
| API/后台任务慢 | 服务/外部依赖分段耗时、查询/锁/连接、队列等待、数据规模 |
| 吞吐下降或资源增长 | 并发/到达率、积压、CPU/内存/IO/连接预算和运行时间 |

为主要指标记录单位、统计口径、样本/时间窗口、版本/配置、设备/运行时、数据规模、负载、缓存冷暖、预热、测量工具与预算，保留原始证据位置。按症状选择指标；均值、分位数和资源数据各有用途，不能用单个平均值隐藏长尾，也不从少量样本报稳定 p99。控制实验支持定位/回归，获授权的真实使用数据支持实际体验；二者分开报告，不把本地/浏览器分数推广到原生或真实用户。

从证据定位耗时或资源消耗路径，提出可区分假设；数据库专项按实际引擎/版本处理，使用 PostgreSQL 时可按需读同包 postgres-data.md。没有瓶颈证据不先加缓存、索引、并发或微服务；需要新增信号时交观测能力设计，不在两处各埋一套。

## 优化、比较与保留决定

优先改变可归因的一个因素；必须联动的改变写明因果和测量限制。端内编码采用现有实现约束，已选 TDD 就在同一循环内执行；本技能不再另写第二套实现或重复策略选择。确认身份、验证、数据新鲜度、事务、错误恢复和业务工作量没有因“优化”被削减。

用匹配基线的条件/负载/统计口径复测，按需要重复并观察波动。收益处于测量噪声内就不能报改善；没有可比较基线时可报告测值但不报提升比例。决定保留、继续调查或撤回本任务优化，记录理由及失败尝试结论，避免后续重复无效实验。撤回仅限本任务可确认增量，保留用户和其他任务改动，不用整文件/分支回退。

稳定收益和正确性证据满足目标后停止。预算和回归观察按项目实际需求设置，复用已有 CI/信号；不套固定包体、接口耗时、提升比例、测试覆盖率，也不为了观察自动引入外部服务。结果交完成前证据核对，真实发布另按已有授权进行。

组合分阶段使用时，前置阶段只形成/承接测量方案、基线与瓶颈假设；优化并入唯一端内实现/TDD循环，后置阶段只核对复测、正确性和保留决定，已有有效部分不重跑。项目已有记录直接引用，缺记录时可用本技能的性能记录模板。
