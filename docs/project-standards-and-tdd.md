# 项目规范目录与 TDD 执行约定

## 项目规范放在哪里

老项目沿用已存在且真实负责工程规则的目录/入口，补全已有项目 Skill 的引用，不创建平行的另一份规范。新项目先检查脚手架和团队约定；没有既定位置才使用 docs/engineering/PROJECT_STANDARDS.md，前后端可拆章节或同目录子规范。

项目规范级 Skill 放在当前宿主实际支持的项目级发现目录，优先复用项目现有技能目录。它只提供触发范围、读取顺序、指向现行规范的相对路径和维护方式；规范正文不复制到多处。不同宿主目录不能混为一谈，也不写用户全局目录。目录不同就重新计算路径；建立文件、结构校验、实际宿主发现分别报告。

入口结构见[项目 Skill 模板](../templates/project-skill.md)，正文结构见[工程规范模板](../templates/project-standards.md)。模板本身不是已完成的项目规范，必须填入真实项目事实并核对路径。

## 当前 TDD 怎么处理

TDD、验证范围和测试保留是独立决定。TDD 不默认开启；用户已选就按该范围执行，不反复确认。轻微文档/文案不自动新增测试。没有长期资产要求且无其他项目约定时，新增验证默认 P1；已有测试保留，按实际项目规则运行和维护。

| 策略 | 执行与保留 |
| --- | --- |
| P0 | 不新增/运行自动测试，保留规定工程检查；代码推演不冒称行为验证 |
| P1 | 临时验证，无持久新增，包括不把临时断言长期追加到旧文件；优先外部工作区，原生工具必须项目内时限定已约定的任务临时路径 |
| P2 | 维护有实际回归价值的用例；新增前查已有覆盖，按模块和现有结构组织，旧用例去重/删除遵守授权 |

已经选择 TDD 时：最小真实失败 → 最小实现 → 必要重构 → 最终版本局部验证。同一轮复用载体，不按尝试次数新建编号文件，也不把历次任务滚进一个巨型文件。实现后补检查如实称为回归验证，不删除原实现制造红灯。

## 测什么、用什么测

先从项目规范、构建清单和已有用例锁定语言、运行时、测试根、工具和精确局部命令。Java 使用项目已有 JVM 框架及 Maven/Gradle 入口，前端逻辑/组件使用已有 JS/TS 工具，浏览器行为使用获准的实际浏览器能力；这些说明不授权安装新框架。

不另用 Python 复制 Java/前端逻辑或匹配源码文本，随后宣称相应功能通过。Python 编排器若真正调用既有真实进程/API，只支持其明确的黑盒接口证据，不能代替端内单元、组件或 UI 验收。Python 产品/工具仍可使用 Python 验证；本集合本身的 Python 工具检查属于这种情形。

每次交付核对最终测试 diff、临时文件/断言、重试副本、fixtures、报告/截图、入口和专用依赖，按本任务清单处理并报告结果。只清理本任务已约定的不保留部分，不批量删原测试或整个 target。环境不足或清理受阻如实列出，不制造通过、不静默积累。

本轮修改的是通用技能说明与模板，没有修改任何真实 Java/前端产品，也没有声称已复现或修复用户历史项目中的测试堆积。
