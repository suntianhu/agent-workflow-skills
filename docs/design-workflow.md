# 从头脑风暴到各端设计

1.4.0 为设计新增两项单独职责，总计 **26 技能、8 套组合**。覆盖 Web/后台、各宿主小程序、iOS/iPadOS、Android、桌面及跨端界面；手表、TV、车机、XR 等先按实际目标确认官方规则，不宣称已具备所有平台的专项细则。

## 只设计一个页面时

1.4.1 明确独立设计入口：最小需求→必要参考→页面视觉/原型→对应核对→交付停止。直接使用 aw-requirements-design 和 aw-ui-design 的适用部分，参考只在有缺口时研究；不因没有项目规范、语言或框架而先新建工程、项目级 Skill 或整套体系。

无目标项目时为本页设够用的局部规则；老项目只看稿时读取已有规范、相关页面与本页业务约束，可以在全仓阅读未完时先交草案，并标明未核实实现约束。用户要求“看效果”时交付可查看稿，不能只交文字方案。独立可点 HTML/CSS 等产物不代表用户已选产品栈，模拟状态也不代表真实业务。详见[单页分流](../guides/standalone-page.md)。

老产品的新需求必须先看相关旧页面/截图或预览及实际组件/样式，继承配色、字体、密度、导航和交互。没有 DESIGN.md 不等于从零设计；把原型放到仓库外也不改变这一点。稿件与旧页面做连续性对照，缺关键视觉证据只交标明限制的结构草案，未获改版要求不另起风格。

即使业务完全不同，也继承所属项目的字体/字级、颜色语义、间距、主题、图标和通用组件；找不到相似业务页时查公共样式与基础组件。新设计可重组内容和流程，在同一体系内扩展组件，不能因此放开全局样式或修改字体依赖/主题。

只有转为正式实现/接入项目时才执行相应新旧开发门禁，批准界面稿不替代全仓理解或授权后端。编写可运行原型代码或执行自动交互前先定局部验证，保留用户要的原型文件，仅按约定清理临时验证产物。

## 完整设计职责

| 阶段/技能 | 主要产物 | 职责边界 |
| --- | --- | --- |
| aw-requirements-design | 头脑风暴、目标/非目标、任务结构、行为/状态和验收 | 开放方向才展开，明确小改直接推进；不决定配色和字体 |
| aw-github-reference | 同栈工程范本、固定提交和规范采纳 | 代码组织与工程规则的依据，不以截图代替代码质量 |
| aw-design-reference | 平台/系统/案例的实际阅读证据和采纳表 | 说明借什么、改什么、为什么不用；不把图库当完整体验或素材授权 |
| aw-design-standards | 共用信息/内容/视觉、token/组件、平台映射和规范入口 | 复用项目已有规范；单页局部调整不重建体系 |
| aw-ui-design | 具体页面/流程、原型、局部布局和反馈 | 应用共用规范，变更共享规则才回写；不重复需求审批 |
| aw-frontend-implementation / aw-evidence-verification | 实际目标代码与对应验证证据 | 测试策略先定；文档、Web、原生工具和真机分别报告 |

这些阶段是条件交接，可由同一执行者完成，不要求为每步新建文档、开代理或请求批准。用户已有决定直接承接；必要答案缺失时只保留依赖部分待定。可运行原型代码/自动交互调查也先承接同一次验证策略，不能借设计阶段绕过门禁。

## 参考去哪里找

先看项目已有品牌、规范和真实组件；再查目标平台官方资料。iOS 查 Apple HIG，Android 查 Android Design，微信小程序查其官方设计/组件，桌面查系统设计和实际 WPF/WinUI/AppKit/Qt 等框架资料。跨端分别核对每个发布宿主。

成熟系统可针对问题借鉴，例如 Carbon 的语义规则、GOV.UK 的表单与恢复。真实产品任务流用于比较操作；Mobbin、Dribbble、Behance、Awwwards 等图库仅作灵感候选。记录真正读到、看到、操作到什么；当前网页取证与访问缺口见[参考记录](../provenance/design-references.json)，并非每个入口已读或素材已授权。

UI UX Pro Max 的需求/全局与局部规则已在原指南中吸收；本版补读 Impeccable 的既有设计提取与平台适配，以及 wshobson/agents 的设计体系、移动平台和交互方法，并补充 obra/superpowers 的头脑风暴材料。固定提交、文件散列、部分阅读范围与许可见[来源取舍](provenance.md)；没有复制整套技能、搜索库、工具或素材。

## 整体规范放在哪里

继续使用项目已有 DESIGN.md、设计系统文档、token 和组件源，由项目规范唯一入口引用。若团队已有 docs/team，就沿用该目录；只有确无现行约定才使用项目规范默认目录。设计内容少时写原规范章节，多时才在同一规范目录拆子文档，使用[设计规范模板](../templates/design-standards.md)填真实依据。

项目规范级 Skill 放在该项目宿主实际支持的技能发现目录，只有范围、触发、同一规范的真实相对引用与维护方式；从 SKILL.md 所在目录核对路径可读且未离开项目。晚启用设计技能仍读取同一全仓基线、技能采纳表、冻结区和测试决定。文件存在、相对路径可读、宿主实际发现分别留证，不把规范模板安装为已完成技能。

## 各端共用什么，分别核对什么

品牌语义、内容和业务意图可以共用；导航/返回、原生控件、单位/字体、安全区、键盘/焦点、权限与生命周期按目标平台映射。见[平台分流](../guides/design-platforms.md)。小程序网页卡片只借信息层级；Android 不因喜欢 iOS 风格换成 Expo；WPF 密集录入优先真实键盘效率。支持范围决定核对矩阵，浏览器预览不证明小程序或原生已适配。

五个 UI 相关组合包含条件设计阶段。纯 API bug 跳过设计参考、整体设计体系和 UI；局部文案/间距直接应用现有规则；只有共享组件/token 改变才扩大受影响消费者。TDD、本端工具链和临时测试保留仍沿用原项目政策，不追加永久测试来证明技能文档修改。

## 本次验证边界

旧/新指南的四个独立合成场景均能守住主要约束；新内容补足来源分层、具体平台检查项、职责与模板，不能由此宣称旧版必然失败或测得能力提升。结构、导出和场景检查见[验证记录](validation.md)。本版没有实际渲染产品界面、执行各端交互、重跑原生宿主发现或测量提效。
