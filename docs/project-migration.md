# 项目迁移用法与职责

`aw-project-migration` 处理已有产品更换前端、管理端、服务端、ORM/数据库或架构时的跨端迁移编排。迁移与后续性能/观测、工作流采纳纳入 1.2.5，共 29 技能/九组合。入口与资料经现有生成器维护；[通用职责与去重](adoption-integration.md)记录交接，本机加载证据另列。

## 最短使用方式

先读 [SKILL.md](../skills/aw-project-migration/SKILL.md)。需要完整的条件能力集合时，使用 [project-migration.json](../bundles/project-migration.json)；它是文档清单，不是自动执行引擎：

```sh
python scripts/export_bundle.py --bundle project-migration --include-optional --out ../migration-workflow-export
```

导出目录必须全新且在集合之外，导出不等于安装。`--include-optional` 携带协作技能，不授权启动代理。单独复制本技能完整目录也能使用，其他技能只按实际缺口组合。

可用提示词示例（示例未指向真实项目）：

> 分析这个已有产品更换框架的迁移需求。先沿用项目规范和有效代码基线，确认真实目标与保留项，覆盖前端/管理端、服务、请求接口、回调、定时任务、历史数据和附件。交付迁移方案、业务分批任务图、兼容/对账和切换恢复条件，先停在方案交付。目标技术栈若未确定，给适配现有资产的候选与依据。考虑多智能体的文件所有权和依赖，但先不要启动代理或操作生产。

正式实施时，在上面增加具体实施范围、既有目标决定、允许环境/数据与委派授权；技能会复用这些决定。不要为了填写模板要求用户重复提供仓库已有信息。

## 五个关键产物

1. **迁移简报：** 为什么迁移、要改变什么、保留什么、明确不做什么，以及语言/平台、窗口和恢复目标。
2. **保留/改变台账：** 旧证据 → 消费者/触发 → 期望行为 → 目标落点 → 验收；未知与下线分开。
3. **目标与过渡方案：** 比较原位演进、业务分批或窗口切换，明确数据权威写入方、任务执行权与兼容期限。
4. **业务批次任务图：** 先贯通样本，再列依赖、可并行工作、独占文件/数据环境、集成点和完成判据。
5. **切换与恢复记录：** 数据增量与对账、任务/回调在途处理、具体切换顺序、恢复限制、观察和退役条件及实际证据。

[计划模板](../templates/project-migration-plan.md)为可选起点，已有文档直接复用。接口/任务细项见[保留指南](../guides/migration-preservation.md)，数据和恢复见[执行指南](../guides/migration-execution.md)，分工见[协作指南](../guides/migration-agents.md)。

## 与现有流程的关系

新建迁移目录仍是老产品：正式代码实施需要有效完整代码理解和同一项目规范，不能切到新产品组合跳过旧行为。目标栈选择在迁移方案内结合现有资产评估，`aw-framework-selection` 的真正新产品边界保持原样。已确定的栈不反复比较，已选定后缺工程范本才接 `aw-github-reference`。

迁移技能拥有保留映射与过渡顺序，接口契约交 `aw-api-contracts`，端内实现交前/后端能力，数据/任务实施属于后端。验证策略先于实际实现/行为检查；选 TDD 时由其循环统筹实现。多智能体按业务任务和独占所有权安排，不按技能数量启动。真实切换需具体授权，方案或本地演练不自动变成发布。

## 来源与未采纳做法

2026-10-21 研究三个固定提交的公开技能及官方技术资料。采纳和排除记录见[来源说明](provenance.md)及[迁移参考记录](../provenance/migration-references.json)。不继承专用代理名称、强制派人、固定覆盖率/灰度比例/观察天数、无条件双写或“所有迁移都能无损回滚”的承诺。项目真实需求及本集合现行门禁优先。

## 验证范围

当前检查结果另记在[验证记录](validation.md)。结构校验、导出与文字边界推演不能证明已迁移真实产品、生产数据已对账、调度器端到端不重复，或多智能体运行效果已测量。宿主发现和模型任务未验证时也要单独标注。
